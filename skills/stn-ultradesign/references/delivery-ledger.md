# Machine-checkable delivery conformance

Use this small binding record when substantial delivery, changed requirements or contributor handoffs need mechanical reconciliation. A focused task can use a few records. It implements the trace in [requirements-conformance.md](requirements-conformance.md), not another requirement register or application inventory. Existing project records remain authoritative; IDs and references connect them. Copy [delivery.template.json](../assets/delivery.template.json) into the target project's private evidence directory and fill it from the actual work.

## Bind before execution; reconcile before a claim

1. Reconcile source requests and current decisions. Plan observable obligations for each required stage and affected usage/context. Assign each obligation its exact artifact, environment and required evidence methods.
2. Run `python3 <skill>/scripts/delivery_check.py delivery.json --fingerprints`; for linked audit obligations use `python3 <skill>/scripts/delivery_check.py delivery.json --fingerprints --audit audit.json` with the same current audit used for validation. Register audit check IDs and intended evidence descriptors/references before capture. Record each current fingerprint in the test run's `obligation_bindings` **before** exercising that obligation. The digest binds the requirement, decision, obligation, artifact and contract revision; linked audit behavior, context, relevant entities and exact evidence descriptors are also bound. Even a text change without a version bump invalidates it. Missing audit data produces no fingerprint for its linked obligations.
3. Execute the actual inspection/test in the stated context. Record the observation, method and exact artifact revision, then link the result through a check. Preserve unavailable execution as `blocked` or `not-tested`; a simulated concept is not application verification. The helper runs no browser or tests and imports no test-runner output automatically.
4. Record available local evidence files with their SHA-256 hashes after capture. Check with `python3 <skill>/scripts/delivery_check.py delivery.json --require-ready --evidence-root <private-evidence-directory>`. For an existing audit, also provide `--audit audit.json`. Inspect both readiness gaps and file-integrity results.
5. A changed binding requires fresh affected execution, or a separately justified carry-forward review recorded as new evidence within the existing audit rules. Replacing only a check's fingerprint cannot reuse a stale run. Never relabel an old result or refresh hashes to make a changed file pass.

The output distinguishes valid structure from declared stage readiness. Exit `0` means valid records; exit `1` means invalid records/input; `--require-ready` additionally returns `2` for valid but unresolved work. Without `--require-ready`, exit `0` does not mean ready. `--fingerprints` prints bindings and validation errors only, never a verification claim.

`ready` concerns the declared stage and reconciled model. It does not establish complete discovery, user acceptance, permission, authentic execution or good design. Revision strings and observations are self-reported; the helper cannot prove which build was running. A file hash proves unchanged bytes relative to its recorded hash, not the truth or provenance of their contents. Report those limits with readiness; inspect the evidence itself and conduct the independent review.

## Schema 1

All IDs and named revision/reference fields are nonempty strings; IDs are unique within each collection. Records are JSON objects, collections are arrays, and ID lists contain unique nonempty strings. Keep only current runs/checks here; preserve historical results outside the current record.

| Record | Required fields and meaning |
| --- | --- |
| Root | `schema_version: 1`, `scope`, `requirements`, `decisions`, `artifacts`, `obligations`, `runs`, `checks`. This is separate from audit schema 2; existing audits need no migration. |
| `scope` | `boundary`, `stage` (`concept`, `implementation`, `verification`), `contract_revision`, boolean `reconciled`, `open_questions` (array, possibly empty), `audit_gate` (`none`, `reviewed`, `passed`). Material open questions or unreconciled scope keep readiness open. |
| Requirement | `id`, `revision`, `source_ref`, `outcome`, `status` (`active`, `retired`), current `decision_id`, `required_stages`. Every active requirement needs at least one planned obligation per listed stage. Retirement additionally requires a confirmed/delegated decision, `retirement_ref` identifying actual authorization and `consequences`; a recorded reference is not authenticated approval. Retain the original request and remaining obligations. |
| Decision | `id`, `revision`, `source_ref`, `interpretation`, `state` (`confirmed`, `delegated`, `proposed`, `unresolved`, `superseded`). Active requirements need a confirmed or delegated current decision. |
| Artifact | `id`, `revision`, `reference`, `environment`, `kind` (`concept`, `prototype`, `application`). Use a concrete build/revision and actual runtime environment; an arbitrary label cannot prove either. |
| Obligation | `id`, `requirement_id`, current `decision_id`, `artifact_id`, `stage`, `context`, `expected`, `failure_example`, `required_methods`. `context` references the existing affected usage/context plan; no second inventory is created here. Methods are `source`, `rendered`, `interaction`, `assistive-technology`, `api-observation`. Implementation/verification require an application artifact; verification requires a runtime method. |
| Run | `id`, `artifact_id`, `artifact_revision`, `environment`, `context`, `method`, `observed`, `reference`, `obligation_bindings` (object mapping obligation IDs to their fingerprints), `files` (array, possibly empty). Each run binds at least one obligation. Reference the actual report/capture, never a hypothetical run. |
| Evidence file | Within `run.files`: `path` relative to the explicit evidence root and lowercase `sha256`. List only necessary safe captures/reports; keep credentials and private production data out. Absolute paths, traversal, URLs, backslashes and wildcard paths are rejected. Symlinks escaping the root and non-files cannot satisfy integrity. |
| Check | `id`, `obligation_id`, `status` (`pass`, `fail`, `blocked`, `not-tested`), `observed`, `run_ids`, `binding_sha256`. One current check per obligation. Passed/failed checks require matching runs covering every required method. Blocked/not-tested may have no run; describe the actual reason in `observed`. |

An active requirement with no required stages, unknown IDs, duplicate current results or structurally invalid data cannot pass. Every obligation's stage must appear in its requirement's plan. Missing obligations, stale bindings, unresolved decisions and due checks other than `pass` keep readiness open. Future-stage obligations must already be planned but do not need future results for an earlier stage's claim. The declared current stage needs at least one active obligation of that exact stage: completed concept work alone cannot become implementation or verification readiness by changing `scope.stage`. Earlier requirements can retain their original stages; they need not all be repeated. The report separates all `due_obligations` from `current_stage_obligations`.

Use one obligation per independently verifiable outcome/context. Shared execution can bind multiple obligation IDs when it actually exercises each; every check must still point to the applicable runs and methods. Stage obligations can point to different concept and application artifacts. This prevents a prototype receipt from closing a production check.

## Reuse an existing audit

For an obligation already present in audit schema 2, retain its exact `id`, set `audit_obligation_id` to that same ID, and use the existing `context_id` as `context`. The linked artifact must match the audit's exact revision/environment; its required methods cannot be weakened. Runs add `audit_evidence_ids` referencing existing evidence with matching target, method, revision, environment and context. A linked check must agree with the audit result and bind its evidence IDs. Fingerprints include the audit obligation, full context, owning/referenced entities, current check ID and its evidence descriptors. Changed meaning or a redirected evidence reference invalidates old bindings even when IDs and revision strings stay the same. Unrelated audit rows are excluded. Result status is checked separately rather than fingerprinted, so recording the outcome of a pre-registered run does not invalidate its own plan.

Provide the current audit through `--audit`; a declared link without it remains open. The helper invokes the existing audit validator and returns its separate coverage result. `audit_gate: reviewed` requires that validator's original-request coverage; `passed` additionally requires all planned applicable checks passing. Choose the gate for the actual claim: an investigation can complete with findings, while conformance cannot call those failures passes. `none` makes no audit-completion claim; it cannot waive a full-audit obligation established elsewhere. The original audit remains authoritative for inventory and coverage.

## Integrity modes and limits

Without `--evidence-root`, listed files are explicitly `unchecked`; readiness is only record-based. With that option, the helper hashes explicit files beneath that root and reports checked, changed, unavailable and unsafe files. Missing local files for a used run, a changed/missing declared file or a zero-byte capture keep requested readiness open. A nonempty file is only an integrity prerequisite; its contents still need substantive review. The helper never scans for evidence, searches for secrets, follows network references, executes file contents or repairs a mismatch automatically. Runs without files remain visible in either mode.

The importable API is `validate_and_summarize(data, evidence_root=None, audit=None)` using keyword arguments for the optional values; it returns the same structured result as the CLI. `main(argv)` returns the documented exit code. Use `binding_fingerprints` from validation to record bindings before execution. This helper checks relationships and file integrity; matching records still need meaningful assertions, actual application observation and human interpretation.
