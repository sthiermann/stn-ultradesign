# ThermoDesk concept review — 16 September 2026

**The supplied candidate is not ready for approval of the full-product scope.** It depicts parts of Monitoring, Roles and Messages, but changes or omits required behavior. The owner's “looks coherent” comment supports the appearance only; it approves neither the complete concept nor any feature retirement. Retain the confirmed compact, legible, neutral direction, visible focus, equal device priorities, and end-attached sheets **for object editing**.

The product's primary work is observing selected chambers, comparing their thermal signals and investigating an event without losing selection or time context. Scheduling, access administration and direct conversation support that work. These purposes and role rules come from the supplied baseline, not user research. Real operating capacity, acceptable data latency and the precise summary aggregation are not established.

Evidence below distinguishes **source observations** from **proposed behavior**. I inspected the complete [task](interaction-fixture/task.md), [baseline](interaction-fixture/baseline.json) (`synthetic-baseline-1`) and all 53 lines of [proposal.html](interaction-fixture/proposal.html). I applied STN Ultradesign's task-flow, component, preservation, concept, discovery, brand, analytical, messaging, adaptation and verification guidance and related mapping templates. No archived evaluations, other conversation documents, production code or external sources were consulted. No inputs were changed.

**Actual rendered checks: none.** No browser interactions, keyboard tests, screenshots, assistive-technology checks or user studies were performed. Findings about missing handlers and state follow from source inspection; layout quality, actual focus behavior and device usability remain unverified. The recommendations are product-specific contract proposals, not claims of a universal standard or implemented corrections.

## Revised interaction contract — proposed, not implemented

**C1. Commands belong to the current Monitoring view.** “More actions” opens an anchored command menu. A choice closes it and returns focus to the trigger (or the opened editor); Escape/outside dismissal makes no change. Apply the actual menu keyboard contract and visible focus. There is no intermediate “Refresh now,” “Copy link” or “Reset now” panel.

| Baseline action | What the user does and sees | Retention, failure and return |
| --- | --- | --- |
| Refresh readings | Choose once; receive pending feedback, followed by refreshed readings or a recoverable error. | Preserve selected chambers, history interval and all display choices. Keep prior readings distinguishable from failed/stale results; remain in Monitoring. |
| Copy view link | Choose once; copy selection plus the current history instant. Confirm only successful copying. | No saved object is created. Failure leaves the view intact and offers retry; a manual-copy fallback is a proposed platform-dependent recovery. |
| Rename view | Open an end-attached editor identifying the selected saved view, with its current name. Edit, Save or Cancel. | Keep the old name until successful Save; then update selector/list identity. Cancel leaves it unchanged; failure retains the draft. Return to the same view and trigger. |
| Reset arrangement | Choose once; restore that view's default ordering and show Undo. | Undo restores the preceding arrangement within the current session. Selection, history and personal choices remain intact; no confirmation detour for this reversible command. |

**C2. Saved view is a value; display preferences are independent.** Use a labeled single-value selector with North lab selected initially and Stability tests/Evening run available. Choosing another restores its chamber selection and ordering, updates the displayed selected value, and retains personal choices. It does not open an editor or create a saved view.

“Display” opens a compact, anchored settings popover with five independently checkable choices: Keep chamber names visible (false), Show status symbols (true), Event previews (true), Chamber metrics (false), Summary inspector (true). Show their current values and personal scope. Apply each immediately and keep the popover open for further changes; Escape/outside dismissal returns focus without undoing applied choices. Preserve each choice across view/panel changes; agree and verify storage across reloads rather than inventing the baseline's retention duration. Hiding previews must not delete history or acknowledge incidents.

**C3. Inspect thermal evidence in Monitoring.** When Chamber metrics is on, each chamber shows Ambient ○ 23.4 °C, Probe ◇ 28.2 °C and Target □ 28.0 °C with distinguishable simultaneous traces, their supplied history, and a shared “Past 60 seconds” time axis. Pointer, touch and keyboard can select a trace/sample to expose exact value and time while the other traces remain visible. The fixture provides ordered values but no exact sample timestamps: obtain or explicitly define synthetic timestamps before demonstrating exact-time inspection.

Show the Probe threshold at **≥30.0 °C** and its quantity/unit. “Edit threshold” opens the object editor for the identified chamber only when `threshold.write` applies within assigned scope. Validate against the actual domain contract, retain input on failure, and update the visible threshold after successful Save. Cancel changes nothing. Values just below, at and above 30.0 must demonstrate the inclusive event rule; no invented hysteresis or debounce.

Summary inspector is a nonmodal Monitoring inspection region, independently controlled from on-chamber metrics. It retains the selected chambers and time alignment and can coexist with metrics and Messages. **The aggregation formula is unresolved:** obtain the intended decision and calculation before labeling a combined temperature. Do not silently replace the candidate's number with an invented mean or maximum. Returning from sample/incident detail restores the previous selection, history position and relevant focus, without an automatic jump to now.

**C4. Events are retrievable incidents, not generic notices.** At the lower start edge of the Monitoring workspace, show at most three previews, newest nearest the bottom. Each has chamber illustration/name, event time, measured value, threshold and Open incident. For the four-event fixture, show e2/e3/e4 with e4 at the bottom and one older event indicated through an overflow count/history entry; preserve all four in history. This is the proposed overflow presentation of the baseline's required limit.

Each preview lasts 12 seconds, pausing while hovered or keyboard-focused; individual dismissal leaves other previews, history and incident acknowledgment unchanged. Open incident takes the user to the authorized chamber/event at its time, then returns to the prior Monitoring context. History remains reachable after all previews expire or are disabled. Keep acknowledgment separate and offer it only with `incident.acknowledge` in scope; its detailed result contract still needs depiction. At 30.0 °C, Chamber C qualifies under the inclusive rule.

**C5. Conversation belongs to the messenger.** Messages opens its own region without changing the chamber selection. Inside it: conversation list → New conversation → choose Alex Morgan or Sam Chen → compose → Send → visible new message in the correct conversation → Back to conversations. Return to Monitoring closes/collapses only the messenger. Display recipient identity while composing; retain selected recipient and unsent text through Back, closing, reopening, panel changes and resizing. A failed simulated send retains text and offers retry; clear the draft only after the fixture's successful send and visible thread update. Do not invent delivery/read-receipt guarantees.

In **docked mode**, recipient selection and composition occupy the messenger region beside Monitoring, using a local sequence if narrow. In **expanded mode**, use that expanded workspace with a visible “Return to monitoring”/collapse control. In **compact mode**, use the same list → recipient/compose → thread sequence in a single pane, with explicit Back and Close. State survives all mode changes. The messenger is independent of the selected chamber and does not reuse the global application modal for its local setup.

**C6. Apply the editor family only to actual objects.** Rename view, per-chamber threshold, schedule create/edit, person-role assignment and custom-role create/edit use consistent end-attached sheets in their owning workspace: identifiable target, labeled heading, close control, Save/Cancel, local validation, pending/success/failure, initial focus and return to the invoking object. Proposal: workspace-modal while editing; no background edits, and sufficient Monitoring context remains recognizable. Dirty close/Escape offers keep editing or discard instead of silently losing work. On compact space the end-attached sheet may fill its owning region; its fields and actions must remain reachable with keyboard/zoom. Exact dimensions and motion remain proposals for rendered review, not approved constants.

**C7. Restore administration using real records.** Roles lists Observer, Technician and Coordinator, opens their actual grants, and offers Create custom role. Observer is inspectable but not editable. Permitted custom-role edits change the selected role's name and individual grants; Save returns to that updated record, Cancel retains the original. Read/Act/Manage may be explanatory group headings, never replacement roles or permission keys.

Preserve `chamber.read`, `incident.read`, `incident.acknowledge`, `threshold.write`, `schedule.write`, `people.assign`, and `role.write` individually and the baseline role combinations. Intersect grants with assigned chamber scope; Coordinator does not acquire threshold editing by managing people. People → selected person shows assigned chamber scope and supports assigning an existing role with `people.assign`; role definition editing belongs under Roles with `role.write`. Schedules → list → create/edit → saved schedule/next run → return preserves the selected list context; writes require `schedule.write`. Schedule fields, recurrence/timezone semantics and actual person records are absent from the fixture and remain design inputs, not invented working features. Out-of-scope chamber content must never be shown; this concept cannot certify server enforcement.
