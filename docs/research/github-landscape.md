# GitHub landscape for an independently developed design skill

**Access and comparison date: September 16, 2026.** This review concerns published capabilities and evidence, not adoption of other skills. Materials read were repository overviews, README descriptions, license metadata and a linked case study. No third-party skill was installed, executed, cloned or incorporated into this package. Repository instructions were not executed as working instructions. Sources point to changing default branches; a reproducible future comparison must record exact revisions.

## What the reviewed projects offer

### UI UX Pro Max

[nextlevelbuilder/ui-ux-pro-max-skill](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill) describes a searchable collection of design and technology recommendations, along with generation and persistence of project-specific design rules. Its current overview lists many styles, palettes, font combinations, chart types and web/native technologies. It also documents accessibility, robust text rendering, version awareness and catalog maintenance.

**Documented strength:** broad structured coverage and quick access to concrete design suggestions. **Question for evaluation:** catalog size does not establish whether recommendations address the right user problem or reliably improve complex workflows. An illustration or demonstration is not a comparative experiment. The README explicitly describes a linked historical video as inspiration rather than a benchmark. This does not establish that the project has no other tests.

**License metadata:** the [license file](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill/blob/main/LICENSE) states MIT. This project uses none of its datasets, source code, templates or instruction text.

### Impeccable

[pbakaus/impeccable](https://github.com/pbakaus/impeccable) documents considerably more than stylistic advice: product context, design before implementation, critique, technical audits, responsive adaptation, browser iteration and deterministic checks. The overview read on the access date lists 24 commands and 61 deterministic rules. These are publisher-reported counts for that version, not independently verified coverage.

**Documented strength:** connecting design work, project context and practical browser inspection. **Question for evaluation:** a detected stylistic issue is not automatically a user problem; explicitly opinionated rules need context. It would be inaccurate to claim this project lacks concept development or audits.

Its [Neo-Mirai case study](https://impeccable.style/cases/neo-mirai/) illustrates the described progression from visual references to a responsive website with browser-based corrections. It is a demonstration; the page read contains no controlled comparison with user outcomes.

**License metadata:** [LICENSE](https://github.com/pbakaus/impeccable/blob/main/LICENSE) states Apache 2.0. This project does not reproduce its extension of others' work; our materials are independently authored.

### Vercel Agent Skills

[vercel-labs/agent-skills](https://github.com/vercel-labs/agent-skills) contains several specialized skills. The reviewed overview describes React/Next.js performance rules and UI code review addressing semantics, focus, forms, motion, navigation, touch, internationalization and rendering. README rule counts describe scope, not measured quality rankings.

## Supported conclusion

The landscape already goes well beyond selecting attractive colors for AI-generated interfaces. Some projects connect context, design, implementation and testing. This repository should therefore claim neither an invented gap nor superiority based on rule count. The reviewed overviews and case study provided insufficient controlled evidence for a universal ranking of usability outcomes. That is a limitation of this investigation, not a statement about every unpublished or separately published evaluation.

The following development goals come from this project's requirements and primary research. They are neither copies of other modules nor demonstrated competitive advantages:

| Our goal | Observable result |
| --- | --- |
| Inspect the complete application with traceability | Inventory of views, roles, states and important workflows with visible coverage gaps |
| Agree the concept collaboratively | Versioned design with assumptions, alternatives, user approval and implementation mapping |
| Weight recommendations appropriately | Distinguish standards, conventions, user evidence, hypotheses and stylistic decisions |
| Address domain workflows | Testable error, resumption, conflict and permission scenarios |
| Preserve analytical correctness | Data contract, checked transformations and realistic comprehension tasks |
| Demonstrate improvement | Before/after results for the same tasks, including limitations and regressions |

## An original procedure for a future benchmark

This procedure was designed for this project. It has not yet been executed as part of this research.

**Define the tasks.** Use a small, deliberately varied collection of existing applications: an administration interface, analytical dashboard, multistep process, touch-oriented application and text-heavy service. Starting projects must be independently created or legitimately available for the experiment. Tasks include realistic states and identical desired outcomes. Record the starting interfaces' strengths and weaknesses in advance.

**Keep conditions comparable.** Record model, version, tools, starting revision, time/token budget, task description and permitted libraries. Give each candidate the same necessary project information. Handle concept approvals under a predefined procedure so additional human assistance does not silently change the comparison. Repeat runs because generated results vary.

**Evaluate qualities separately.** Where practical, visual reviewers should not know which skill produced an output. Separately check task success, errors, recovery, different input methods, responsive stability, data correctness and technical regressions. An aggregate score must not allow attractive styling to offset serious failures. Reviewers need shared scoring anchors and severity examples.

**Count false alarms.** Audit evaluation should measure more than the number of suggestions. Record confirmed problems, missed known defects, false claims, unusable recommendations and rework costs. For redesigns, verify preserved functionality and accidentally removed capabilities. For concepts, assess decision clarity and the fidelity of subsequent implementation.

**Report results openly.** For each task, show raw values, repetition counts, permitted interventions and remaining uncertainty. Include unsuccessful runs as well as good individual examples. If a method helps only certain application types, state that boundary. Until this evaluation is performed, “better” remains a development goal. Stars, downloads and impressive screenshots do not replace it.
